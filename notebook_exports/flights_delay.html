✈️ Projet Data Science — Retards de vols US¶

Notebook étudiant — version guidée¶

Contexte métier¶

Vous travaillez pour une compagnie aérienne.
L’objectif est d’aider les équipes opérationnelles à mieux comprendre et anticiper les retards.

Vous devez produire :

  1. une analyse exploratoire (EDA),
  2. un dashboard interactif,
  3. un modèle de prédiction,
  4. des recommandations métier.

Règle importante¶

  • L’EDA et le dashboard peuvent utiliser le dataset complet.
  • La partie modélisation devra fera l'objet d'un choix d'échantillonage

Environnement Python¶

  1. Ouvrez un terminal (macOS/Linux) ou l’invite de commandes / PowerShell (Windows).
  2. Accédez au dossier de votre projet avec cd chemin/vers/votre/projet
  3. Créez l’environnement virtuel en exécutant :
    • macOS/Linux : python3 -m venv env
    • Windows : python -m venv env
  4. Vérifiez l’activation en confirmant que votre invite de commande est préfixée par (env)
  5. Installez les paquets dans l’environnement avec pip install nom_du_paquet
  6. Listez les paquets installés avec pip list ou sauvegardez les dépendances avec pip freeze > requirements.txt
  7. Désactivez l’environnement lorsque vous avez terminé en tapant deactivate

Disponibilité Colonnes
Avant le vol (potentiellement prédictives) YEAR, MONTH, DAY, DAY_OF_WEEK, AIRLINE, FLIGHT_NUMBER, TAIL_NUMBER, ORIGIN_AIRPORT, DESTINATION_AIRPORT, SCHEDULED_DEPARTURE, SCHEDULED_ARRIVAL, SCHEDULED_TIME, DISTANCE

Cible / leakage direct ARRIVAL_DELAY (cible), DEPARTURE_DELAY, AIR_SYSTEM_DELAY, SECURITY_DELAY, AIRLINE_DELAY, LATE_AIRCRAFT_DELAY, WEATHER_DELAY

⚠️ Data leakage critique :

  • ARRIVAL_DELAY est notre cible — on en dérive IS_DELAYED à la section 6.
  • DEPARTURE_DELAY est tentant mais reflète un événement après l'heure programmée de départ. On se place avant le vol → on l'exclut des features.
  • Les *_DELAY décomposés (AIR_SYSTEM, SECURITY, AIRLINE, LATE_AIRCRAFT, WEATHER) sont des post-mortem causaux — uniquement renseignés pour les vols déjà retardés (~80 % de NA).

7. Feature engineering¶

Créez quelques variables simples pour l’analyse.

Suggestions :

  • heure prévue de départ à partir de SCHEDULED_DEPARTURE
  • indicateur week-end
  • éventuellement période de la journée : matin / après-midi / soir

Attention : les colonnes ORIGIN_AIRPORT et DESTINATION_AIRPORT peuvent contenir un mélange de nombres et de texte.
Pour éviter des erreurs plus tard, vous pouvez les convertir en texte.

In [7]:
# Cast en str pour éviter les surprises (certains codes aéroports sont alphanumériques)
for c in ["ORIGIN_AIRPORT", "DESTINATION_AIRPORT", "AIRLINE"]:
    df[c] = df[c].astype(str)

# Heure prévue de départ : SCHEDULED_DEPARTURE est au format HHMM (ex: 1435 -> 14h)
df["SCHEDULED_DEP_HOUR"] = (df["SCHEDULED_DEPARTURE"] // 100).clip(0, 23).astype("int8")

# Période de la journée
def _period(h: int) -> str:
    if h < 6:  return "nuit"
    if h < 12: return "matin"
    if h < 18: return "après-midi"
    return "soir"
df["DEP_PERIOD"] = df["SCHEDULED_DEP_HOUR"].map(_period).astype("category")

# Week-end (samedi=6, dimanche=7 dans ce dataset)
df["IS_WEEKEND"] = (df["DAY_OF_WEEK"] >= 6).astype("int8")

Synthèse — 3 insights métier (C3.3)¶

  1. Saisonnalité bimodale : les pics de retards apparaissent en janvier-février (~21-23 %, dominante météo hivernale) ET juin-juillet (~21-23 %, vacances scolaires + orages d'été), avec un rebond en décembre (~20 %). Septembre-octobre forment le creux annuel (~12 %). → Recommandation : pré-positionnement d'équipes opérationnelles renforcées sur ces 5 mois.

  2. Effet « cascade horaire » : le taux de retard augmente quasi-linéairement avec l'heure de départ — un vol programmé en soirée (>18 h) a 2 à 3× plus de chances d'être retardé qu'un vol matinal. La cause est connue : les retards se propagent au fil de la journée via les rotations d'appareils (« late-aircraft delays »). → Recommandation : prévoir des marges horaires plus larges en fin de journée.

  3. Forte disparité entre compagnies et aéroports : les compagnies low-cost (Spirit 28,8 %, Frontier 25,4 %) et le top 5 aéroports dégradés (LGA, ORD, MIA, BWI, DAL — tous ~20-23 %) contrastent avec les compagnies majors (Hawaiian 10,5 %, Alaska 12,3 %, Delta 13,0 %) et les hubs d'Hawaii (HNL, OGG, KOA, LIH — tous <12 %). → Recommandation : audit opérationnel ciblé sur les 5 aéroports les plus dégradés (concentrés sur l'axe Nord-Est / Midwest).

def evaluate_model(name, model, X_eval, y_eval, train_time_s):
    """Évalue un modèle et retourne un dict de métriques."""
    y_pred = model.predict(X_eval)
    y_proba = model.predict_proba(X_eval)[:, 1]
    fpr, tpr, _ = roc_curve(y_eval, y_proba)
    roc_auc = auc(fpr, tpr)

    metrics = {
        "modèle": name,
        "accuracy": accuracy_score(y_eval, y_pred),
        "balanced_acc": balanced_accuracy_score(y_eval, y_pred),
        "f1": f1_score(y_eval, y_pred),
        "roc_auc": roc_auc,
        "train_time_s": train_time_s,
    }

    print(f"\n=== {name} ===")
    print(classification_report(y_eval, y_pred, digits=3,
                                target_names=["à l'heure", "en retard"]))
    print(f"Accuracy         : {metrics['accuracy']:.3f}")
    print(f"Balanced Accuracy: {metrics['balanced_acc']:.3f}")
    print(f"ROC-AUC          : {metrics['roc_auc']:.3f}")
    print(f"Temps entraînement: {train_time_s:.1f} s")

    fig, axes = plt.subplots(1, 2, figsize=(12, 4))
    axes[0].plot(fpr, tpr, label=f"AUC = {roc_auc:.3f}", color="crimson")
    axes[0].plot([0, 1], [0, 1], "--", color="gray")
    axes[0].set_title(f"Courbe ROC — {name}")
    axes[0].set_xlabel("Taux de faux positifs")
    axes[0].set_ylabel("Taux de vrais positifs")
    axes[0].legend(loc="lower right")

    ConfusionMatrixDisplay.from_predictions(
        y_eval, y_pred,
        display_labels=["à l'heure", "en retard"],
        cmap="Blues", normalize=None, ax=axes[1], colorbar=False,
    )
    axes[1].set_title(f"Matrice de confusion — {name}")
    plt.tight_layout(); plt.show()
    return metrics

12. Conclusion¶

Insights principaux¶

  • Saisonnalité bimodale : pics en janvier-février et juin-juillet (~20-23 %) — météo hivernale + vacances été ; creux en septembre-octobre (~12 %).
  • Effet horaire : le taux de retard augmente avec l'heure de départ — les vols de soirée subissent l'accumulation des rotations.
  • Disparité forte entre compagnies et entre hubs : certains acteurs concentrent davantage de risques, ce qui permet de prioriser les plans d'action.
  • Déséquilibre cible : environ 18 % de vols en retard → balanced_accuracy, recall, f1 et roc_auc sont plus pertinents que l'accuracy brute.

Limites¶

  • Données 2015 uniquement : un seul cycle annuel — pas de capacité à modéliser des tendances pluri-annuelles ni l'effet d'évènements exceptionnels.
  • Pas de météo externe : la météo est l'un des principaux drivers des retards mais le dataset n'expose que WEATHER_DELAY post-vol, donc inutilisable comme feature avant départ.
  • Aéroports en cardinalité élevée : le One-Hot est limité avec max_categories=50 pour garder un pipeline léger et reproductible.
  • Échantillonnage à 150 k pour la modélisation : choix d'écoresponsabilité et de temps d'exécution. Un entraînement sur la totalité pourrait améliorer marginalement les métriques, mais avec un coût compute nettement supérieur.

Recommandations métier¶

  1. Renforcement opérationnel saisonnier sur les mois critiques et les aéroports les plus dégradés : pré-positionnement d'équipes au sol, anticipation des rotations et coordination avec les partenaires.
  2. Marges horaires élargies en fin de journée : ajouter des tampons dans la planification des rotations à partir des créneaux où les retards s'accumulent.
  3. Modèle prédictif intégré au système de planification : afficher la probabilité de retard >15 min avant le départ pour aider les équipes ops, relation client et allocation des ressources.

Recommandation de modèle¶

  • Modèles comparés : régression logistique baseline et Random Forest.
  • Choix recommandé : retenir le modèle obtenant le meilleur compromis entre ROC-AUC, balanced_accuracy et rappel des vols en retard dans le tableau de comparaison. Dans ce notebook, Random Forest sert de modèle opérationnel alternatif car il capture mieux les interactions non linéaires entre heure, compagnie, aéroport et distance.
  • Métrique privilégiée : le rappel sur la classe "en retard" et la balanced accuracy, car le coût métier d'un faux négatif (rater un vrai retard) est souvent supérieur au coût d'un faux positif (alerte inutile).

Stratégie d'intégration IA (C4.1)¶

  1. Pilote sur quelques hubs ou lignes à fort volume pendant 4 à 6 semaines, avec suivi quotidien des prédictions et retards réels.
  2. Intégration SI via API ou batch J-1/J-0 alimentant le dashboard opérations.
  3. Gouvernance : versionner données, features, modèles et seuils ; documenter les variables et les exclusions pour éviter le data leakage.
  4. Explicabilité : fournir aux équipes les facteurs principaux du risque : heure, mois, compagnie, origine, destination, distance.
  5. Monitoring : suivre ROC-AUC, recall, faux positifs, dérive des données et feedback terrain.
  6. Écoresponsabilité : privilégier des modèles sobres, limiter la fréquence de réentraînement et conserver uniquement les données utiles.
